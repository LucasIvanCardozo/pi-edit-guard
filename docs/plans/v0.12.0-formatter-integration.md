# v0.12.0 — Integrate pi-code-formatter (formatter safety net)

## Context

`pi-edit-guard` v0.11.0 ends at: cascade (literal → normalized → fuzzy) + autofix uniform drift + block on ambiguous/fuzzy/no-match. There's no formatter integration; users who want auto-format after edits have to install a separate extension (`pi-lens`, `pi-formatter`, etc.) and that means the model sees raw edits and may try to "fix" whitespace drift mid-turn → surrender pattern.

v0.12.0 adds an **opt-in formatter integration** adapted from [pi-code-formatter](https://github.com/losnappas/pi-code-formatter) (MIT, by losnappas). When the user puts a config file in the project declaring formatter commands + filetypes, the extension runs the formatter after every successful edit and **rewrites the tool_result so the model sees a clean diff (original → formatted), never the intermediate drift state**.

This complements the existing autofix: the formatter becomes the single source of truth for whitespace when it's configured, autofix is the fallback when it's not.

## Design — final flow

```
edit tool_call fires
  ↓
pi-edit-guard cascade (literal → normalized → fuzzy)
  ↓
match found?
  ├─ NO  → BLOCK with consolidated report (unchanged)
  └─ YES
       ↓
       formatter config matches this file?
       ├─ YES → skip autofix, return {kind: 'pass'} (formatter will clean later)
       └─ NO  → try autofix
                  ├─ autofix OK → mutate edits[], return {kind: 'autofixed'}
                  └─ autofix declined → BLOCK with report (unchanged)
  ↓
native edit runs (or doesn't, if we returned block)
  ↓
tool_result fires
  ├─ if (event.isError) → current error-reformat hook (unchanged)
  └─ if (success) AND formatter config matches → run formatter, rewrite tool_result
       ├─ formatter changed content → rewrite details.{patch, diff, firstChangedLine}
       └─ formatter no-op or failed → keep original details, log to debug
```

Key insight from pi-code-formatter's design: the `tool_result` handler returns a new details object with `patch`/`diff`/`firstChangedLine` recomputed from `original → formatted` (not `edited → formatted`). The model sees the atomic final state, never the drift intermediate.

## Three new modules

All in `src/`:

### 1. `src/formatter-config.ts` (new, ~100 LOC)

Pure functions, no I/O at module load (read on demand):

```typescript
export interface AutoformatConfig {
  commands: Record<string, string[]>;   // name → [bin, ...args]
  filetypes: Record<string, string>;      // glob → name
}

export interface ResolvedFormatter {
  name: string;
  command: string[];
  pattern?: RegExp;  // absent = wildcard fallback
}

// Ported from pi-code-formatter with attribution
export async function loadConfig(cwd: string): Promise<AutoformatConfig | null>;
export function mergeConfigs(g: AutoformatConfig | null, p: AutoformatConfig | null): AutoformatConfig | null;
export function resolveFormatters(config: AutoformatConfig): ResolvedFormatter[];
export function findFormatter(formatters: ResolvedFormatter[], filePath: string): ResolvedFormatter | null;
export function compilePattern(pattern: string): RegExp;
```

Config paths (same paths as pi-code-formatter, but with `pi-edit-guard` in the name):
- Global: `~/.pi/agent/extensions/pi-edit-guard/config.json`
- Project: `.pi/extensions/pi-edit-guard/config.json`

`compilePattern` rules:
- `*` → no pattern (wildcard fallback, goes last in priority)
- `*.ext` → `/\.ext$/`
- `/regex/` → `new RegExp(middle)`
- `literal` → `/literal$/`

`findFormatter`: first-pass with patterns (specific wins), second-pass wildcard. **First match wins.**

### 2. `src/format/runner.ts` (new, ~50 LOC)

```typescript
export interface FormatterRunResult {
  /** True if the formatter ran successfully AND changed the file content. */
  changed: boolean;
  /** Full content after formatter ran (whether changed or not). */
  content: string;
  /** stderr if formatter failed; empty string on success. */
  stderr: string;
  /** Exit code if non-zero; undefined on success. */
  exitCode?: number;
  /** Resolved command (for debug logging). */
  command: string;
  /** Wall-clock duration in ms. */
  durationMs: number;
}

export async function runFormatter(
  filePath: string,
  formatter: ResolvedFormatter,
  pi: ExtensionAPI,
): Promise<FormatterRunResult>;
```

Use `pi.exec(formatter.command[0], [...args, "--", filePath], { timeout: 5_000 })` — **not** `child_process.spawn`. This is the cleaner pattern from pi-code-formatter and matches Pi's sandbox/permissions model.

If `result.code !== 0`, return `{changed: false, content, stderr, exitCode, ...}`. Never throws.

### 3. `src/format/tool-result-rewriter.ts` (new, ~80 LOC)

```typescript
export interface RewriteResult {
  details: {
    patch: string;
    diff: string;
    firstChangedLine?: number;
  };
}

/**
 * Compute patch/diff from `originalContent` to `formattedContent`, formatted
 * the way pi's built-in edit tool does it internally.
 *
 * Ported from pi-code-formatter (MIT, losnappas) with attribution.
 */
export function generateRewriteResult(
  filePath: string,
  originalContent: string,
  formattedContent: string,
): RewriteResult;
```

Two helpers internally:
- `generateUnifiedPatch(filePath, old, new)` — uses `Diff.createTwoFilesPatch` from `diff` npm pkg
- `generateDiffString(old, new, contextLines = 4)` — line-numbered diff for display, returns `{diff, firstChangedLine}`

We need to add `diff` to package.json dependencies.

The `diff` package: `npm install diff` → adds `"diff": "^8.0.4"` to dependencies (same version pi-code-formatter uses).

**`export default function`** — register additional hooks:

```typescript
// 1. Resolve formatter config at session start
pi.on('session_start', async (_event, ctx) => {
  const config = await loadConfig(ctx.cwd);
  if (!config) return;
  resolvedFormatters = resolveFormatters(config);
  if (resolvedFormatters.length > 0) {
    ctx.ui.notify(`[pi-edit-guard] Loaded ${resolvedFormatters.length} formatter(s)`, 'info');
  }
});

// 2. Existing tool_call hook — also capture original content if formatter matches
pi.on('tool_call', async (event) => {
  if (event.toolName !== GUARDED_TOOL) return;
  const input = event.input as EditInput | undefined;
  const formatter = input?.path ? findFormatter(resolvedFormatters, input.path) : undefined;
  if (formatter && input?.path) {
    try {
      const absolutePath = resolve(ctx.cwd, input.path);
      const content = await readFile(absolutePath, 'utf-8');
      originalContents.set(absolutePath, content);
    } catch {
      originalContents.set(absolutePath, '');
    }
  }
  const result = await processEditInput(input?.path, input?.edits, {
    source: 'tool_call',
    trustFormatter,
    matchedFormatter: formatter,
  });
  if (result.kind === 'blocked') return { block: true, reason: result.reason };
});

// 3. New tool_result hook for formatter (success path only)
pi.on('tool_result', async (event, ctx) => {
  if (event.toolName !== GUARDED_TOOL) return;
  if (event.isError) return;  // formatter doesn't run on failed edits
  const input = event.input as EditInput | undefined;
  if (!input?.path) return;
  const absolutePath = resolve(ctx.cwd, input.path);
  const originalContent = originalContents.get(absolutePath);
  if (originalContent === undefined) return;  // no formatter matched at tool_call time
  originalContents.delete(absolutePath);

  const formatter = findFormatter(resolvedFormatters, input.path);
  if (!formatter) return;

  const result = await runFormatter(absolutePath, formatter, ctx);
  if (!result.changed) {
    appendDebug({
      timestamp: new Date().toISOString(),
      source: 'tool_result',
      path: input.path,
      edits: [],
      result: 'pass',
      formatterCommand: result.command,
      formatterApplied: false,
      formatterReason: result.changed ? undefined : 'no-change',
      formatterStderr: result.stderr ? result.stderr.slice(0, 500) : undefined,
      formatterDurationMs: result.durationMs,
    });
    return;
  }

  // Recompute patch/diff from original → formatted, return new details
  const rewrite = generateRewriteResult(input.path, originalContent, result.content);
  return { details: { ...event.details, ...rewrite.details } };
});

// 4. Existing tool_result hook for error reformatting (unchanged)
```

**IMPORTANT**: the existing `tool_call` and `tool_result` hooks must be PRESERVED. We're adding new ones, not replacing. Multiple `pi.on('tool_call', ...)` and `pi.on('tool_result', ...)` registrations are allowed and run in registration order.

## Risk assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| `pi.exec` API not available in current ExtensionAPI version | Low (similar APIs exist in `pi` 0.84+) | Verify before implementing; fallback to `child_process.spawn` if needed |
| Pi rejects the `{details: {...event.details, ...}}` return shape | Medium | Spike first: write a 30-line test that loads the extension, simulates an edit, and verifies the model receives the rewritten details |
| Two parallel `tool_result` hooks conflict on order | Low | Pi runs hooks in registration order; formatter hook registered after error hook, formatter runs last (good — formatter sees the final error state if any) |
| The `diff` package adds runtime dependency | Low | 8KB minified, widely used, MIT, same version pi-code-formatter uses |
| Original-content Map grows unbounded across many edits | Low | Cleaned up in `tool_result` after each formatter run; max one entry per active file |
| User sets `formatMode` to disable but we still run formatter | N/A | We're not implementing `formatMode` — formatter is opt-in via config existence; absence = no formatter. Simpler. |

## Open questions for the next session

1. **Should we add a `formatter.enabled` opt-out** in `.pi-edit-guard.json` to disable the formatter even when config exists? pi-code-formatter doesn't have this; we don't need it. Recommend **NO** — keep it simple: presence of config = formatter runs.

2. **Should `pi.exec` be wrapped in a try/catch** to handle the case where the extension is loaded into an older Pi that doesn't have it? Recommend **YES** — silent no-op with debug log if `pi.exec` is not a function.

3. **Should we run formatter even when edit was blocked** (isError)? My recommendation: **NO** — there's no file to format. Confirmed.

4. **Config path naming**: should it be `.pi/extensions/pi-edit-guard/config.json` (matches pi-code-formatter's pattern) or `.pi/extensions/pi-edit-guard/formatter.json` (more specific)? My recommendation: **`config.json`** for consistency with pi-code-formatter's schema. The config currently only has formatter settings; if we add other settings later, we can split into sub-files.

5. **Should we add the `registerFlag` pattern** for `PI_EDIT_GUARD_FORMATTER` env var as an override? pi-code-formatter doesn't have it. My recommendation: **NO** — keep it simple, config file only. If user wants to disable in a project, they don't put the config file. If they want to disable globally, they don't put the global config.
